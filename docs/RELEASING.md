# Releasing Den

How changes reach `main` and how a version is published. The day-to-day
rules for branches and pull requests are in [CONTRIBUTING.md](../CONTRIBUTING.md).

## Branches

| Branch | What it holds | How changes arrive |
| --- | --- | --- |
| `feature/…`, `fix/…`, `docs/…`, `ci/…` | one change in progress | commits from its author |
| `dev` | everything merged and not yet released | pull requests, squash-merged |
| `main` | the released code; every commit a tag points at is here | release pull requests from `release/…` branches, and hotfixes, with a merge commit |
| `release/vX.Y.Z` | one release on its way from `dev` into `main` | cut from `dev`, with `main` merged in |
| `hotfix/…` | an urgent fix for the released code, branched from `main` | commits from its author |

`dev` and `main` are protected: changes only by pull request, the `ci-passed`
check must pass, no force-push, no deletion. Tags `v*` cannot be moved or
deleted and only maintainers can create them. The commands that set this up
are in [GITHUB-SETUP.md](GITHUB-SETUP.md).

`main` is merged into with merge commits and never squashed, so after a release
`dev` is still an ancestor of `main` and the next release pull request has no
conflicts of its own making. `dev` is not moved up to `main` after a release
(step 7 below): it takes pull requests only, and the next release branch merges
`main` back in.

## Versions

Den is pre-1.0 and follows [semantic versioning](https://semver.org) the way
0.x versions do:

- **0.MINOR.0** for new features, and for any change that breaks something a
  user relies on: a key, a command, a flag, a config setting, the format of a
  state file or of `den events -json`. Say what broke in the release notes.
- **0.MINOR.PATCH** for fixes only, with nothing new to learn.
- **vX.Y.Z-rc.N** for a release candidate. A tag with a `-` is published as a
  pre-release.

The version is the tag. `make release VERSION=vX.Y.Z` stamps it into the
binary and the release workflow checks that `den version` says `den vX.Y.Z`.
There is no version string to edit in the code.

## Release notes

The notes on a GitHub release are two parts:

1. **The tag's message**, written by whoever tags: a one-line summary, the
   changes a user notices, and anything that broke and what to do about it.
   Draft it in the release pull request's description, where it can be read
   before anything is merged.
2. **The list of merged pull requests**, generated by GitHub and grouped by
   label (`bug`, `enhancement`, `dependencies`; see `.github/release.yml`). A
   pull request labelled `skip-changelog` is left out. Pull request titles
   end up here, so write them for a reader.

There is no CHANGELOG file; the releases page is the changelog.

## Cutting a release

1. **Check `dev`.** The latest `ci` run on `dev` is green, the README describes
   what the code does, and `THIRD_PARTY_LICENSES` is current (CI fails
   otherwise).

2. **Open the release pull request** from a release branch cut from `dev`.
   The branch also takes in `main`, so a hotfix released since the last
   release is merged here, where conflicts can be resolved, and never needs a
   merge commit on `dev`. GitHub deletes the release branch after the merge;
   `dev` is untouched.

   ```
   git fetch origin
   git switch -c release/v0.4.0 origin/dev
   git merge --no-ff origin/main     # "Already up to date" unless there was a hotfix
   make test
   git push -u origin release/v0.4.0
   gh pr create --repo GlacierHubAB/den --base main --head release/v0.4.0 \
     --title "Release v0.4.0" --body-file notes-v0.4.0.md
   ```

   The body is the draft of the tag message. Read the diff once more as a
   whole; this is the last look before users get it. A fix found now goes
   into `dev` by pull request first, then into the release branch with
   `git merge origin/dev`.

   **Prove the candidate before any tag.** The exact commit that will be
   tagged passes the whole pipeline on GitHub first, because a tag whose
   release run fails is spent (see "When the release workflow fails"). The
   release pull request's own checks already include the race detector three
   times on two CPUs and, because it goes into `main`, the slow suite. On the
   release branch's tip, also:

   ```
   for i in 1 2 3; do
     gh workflow run heavy.yml --repo GlacierHubAB/den --ref release/v0.4.0 -f ref=release/v0.4.0
   done
   gh workflow run release.yml --repo GlacierHubAB/den --ref release/v0.4.0 -f version=v0.4.0
   ```

   Dispatch with `--ref` the release branch, so the run uses that branch's own
   workflow file (each run gets its own concurrency group); `--ref main` would
   queue the three runs behind each other. The three `heavy` runs and the
   `release` dry run (`ci`, `heavy` and
   `build` on that commit, with no `verify` and no `publish`) must all be
   green. Tag only then. A failure is fixed on `dev` and proven again; nothing
   is tagged on a red or unproven commit.

3. **Merge it with a merge commit** once `ci-passed` is green (the only method
   `main` allows):

   ```
   gh pr merge --repo GlacierHubAB/den <number> --merge
   ```

4. **Tag the merge commit on `main`** with an annotated tag whose message is
   the release notes, and push only the tag:

   ```
   git fetch origin
   git switch --detach origin/main
   git log -1 --oneline                         # the merge commit of the release PR
   git tag -a v0.4.0 -F notes-v0.4.0.md
   git push origin v0.4.0
   ```

   Never `git push --tags`: it pushes every local tag, including ones that
   were never released.

5. **Watch the release workflow.** It runs, in order:
   - `verify`: the tag is `vMAJOR.MINOR.PATCH[-PRERELEASE]`, annotated, and
     its commit is on `main`;
   - `ci`: the whole CI workflow on the tagged commit;
   - `heavy`: the slow suite, and the race detector three times on two CPUs;
   - `build` (after `verify`, `ci` and `heavy`): `make release VERSION=<tag>`
     with the newest Go 1.26 patch and no cache, then checks `den version` and
     `SHA256SUMS`;
   - `publish`: the only job that can write. It checks the checksums again,
     records a build provenance attestation and creates the release with
     `den_linux_amd64`, `den_linux_arm64`, `THIRD_PARTY_LICENSES` and
     `SHA256SUMS`.

   ```
   gh run list --repo GlacierHubAB/den --workflow release --limit 1
   gh run watch --repo GlacierHubAB/den <run-id>
   ```

6. **Check what was published:**

   ```
   cd "$(mktemp -d)"
   gh release download v0.4.0 --repo GlacierHubAB/den
   sha256sum -c SHA256SUMS
   gh attestation verify den_linux_amd64 --repo GlacierHubAB/den
   chmod +x den_linux_amd64 && ./den_linux_amd64 version
   ```

7. **Leave `dev` as it is.** The release merge commits land only on `main`,
   so after a release `dev` is an ancestor of `main` and GitHub shows it
   "N commits behind" although the two trees are the same. `dev` takes changes
   by pull request only (its ruleset refuses any push, even a plain
   fast-forward: "Changes must be made through a pull request"), so it cannot
   be moved up to `main` with a push. Do not switch the ruleset off and do not
   use a bypass to do it. Nothing is lost: the next release branch merges
   `main` back in (step 2), with no content change, and pull requests keep
   squash-merging into `dev` as usual.

   Between releases `dev` is normally ahead of `main` by the pull requests
   merged since the last release and behind it by the release merges. Both
   are expected.

## When the release workflow fails

A tag is never moved or reused once pushed, even when its workflow failed and
nothing was published (v0.3.0, v0.5.0 and v0.5.1 are such tags). Fix the
problem on `dev` the usual way, prove the new candidate as in step 2, and tag
the next patch version. The failed tag stays, without a release, and the next
release's notes say that it was never published.

## Hotfixes

For a fix that cannot wait for the next release from `dev`:

```
git fetch origin
git switch -c hotfix/<topic> origin/main
# fix, test, commit
git push -u origin hotfix/<topic>
gh pr create --repo GlacierHubAB/den --base main --title "<what it fixes>"
```

Merge it with a merge commit once `ci-passed` is green, wait for `ci` on
`main`, then tag the next patch version on `main` as in steps 4 to 6. Then
bring the same fix to `dev` so the next release keeps it: cherry-pick the
hotfix branch's commits (not the merge commit) onto a branch from `dev`, and
squash-merge that pull request:

```
git switch -c fix/<topic> origin/dev
git cherry-pick -x <first hotfix commit>^..<last hotfix commit>
gh pr create --repo GlacierHubAB/den --base dev --title "<what it fixes> (from v0.4.1)"
```

If `dev` has nothing that `main` lacks (`gh api "repos/$R/compare/main...dev"`
shows `ahead_by` 0), skip the cherry-pick and fast-forward `dev` to `main` as in
step 7 instead. After a cherry-pick `dev` is ahead of `main` by those copies,
so step 7 is not possible until the next release brings the two together.

v0.3.2 went this way: `hotfix/den-sock-v0.3.2` from `main`, pull request #1
into `main` as a merge commit, the annotated tag `v0.3.2` on that merge
commit, then pull request #2 with the same three commits into `dev`. After
it, `dev` had the same tree as `main`. A security fix is described plainly in
the pull request and the release notes (what is affected, what to upgrade),
without steps to exploit it.

## Who does what

- Anyone, agents included, opens pull requests into `dev`.
- Maintainers review and merge pull requests into `dev`.
- Maintainers open and merge release pull requests and hotfixes into `main`,
  and push `v*` tags. An agent may prepare a release pull request and its
  notes, but a person merges and tags.

## Go version

The release is built with the newest patch of the Go minor named by
`GO_VERSION` in `.github/workflows/ci.yml` and `release.yml` (now `1.26.x`),
so a standard-library security fix reaches the next release without a code
change. `govulncheck` in CI uses the same Go, so it reports what a release
would ship. `go.mod`'s `go` line is the oldest Go that can build Den; its
`toolchain` line (now `go1.26.9`) makes a local `make release` with an older
Go fetch at least that patch, so a hand-made build does not ship the
standard-library vulnerabilities of 1.26.0. Moving to a new Go minor means
changing `GO_VERSION` in both workflows and the `toolchain` line in one pull
request.
